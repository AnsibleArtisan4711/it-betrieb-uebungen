## Aufgabe

### Aufgabe 1 – API-Token (Einheit 8.2)

Erstelle in den Profil-Einstellungen des Agenten ein persönliches Zugriffs-Token mit Berechtigung zum Erstellen von Tickets. Ist die Token-Anmeldung nicht möglich, ist sie auf manchen Systemen abgeschaltet und muss in den Zammad-Einstellungen aktiviert werden.

### Aufgabe 2 – API testen (Einheit 8.2)

Sende vom Client aus per `Invoke-RestMethod` oder `curl.exe` (in Windows PowerShell ist `curl` ein Alias) einen POST mit dem Token an die Zammad-API (Simulation eines Monitoring-Alarms). Vorlage: `dateien/api-ticket.ps1` (**nicht ausgeführt**, Felder nicht gegen die Ticket-Dokumentation geprüft). Das Token trägst du selbst ein und legst es nie in eine Datei im Repository.

### Aufgabe 3 – Log-Analyse (Einheit 8.3)

Verbinde dich per SSH auf die Server-VM. Beobachte `sudo tail -f /opt/zammad/log/production.log`, während du das per API erstellte Ticket im Webinterface öffnest und schließt. Identifiziere die Zeilen `Started GET` bzw. `Started POST`.

### Aufgabe 4 – Report (Einheit 8.1)

Öffne das Dashboard und, falls berechtigt, den Bereich für Berichte (Menüführung *nicht bestätigt*). Ermittle die Tickets je Gruppe und Status, vergleiche mit deinen Testtickets und erkläre, welche Kennzahl für den Betrieb am wichtigsten ist.

## Hinweise

- `curl` in Windows PowerShell ist ein Alias; nutze `curl.exe` oder `Invoke-RestMethod`.
- Das Log braucht `sudo`.
- Ein Token ist ein Geheimnis: nicht in Dateien, nicht in Screenshots, nach dem Test löschen.
