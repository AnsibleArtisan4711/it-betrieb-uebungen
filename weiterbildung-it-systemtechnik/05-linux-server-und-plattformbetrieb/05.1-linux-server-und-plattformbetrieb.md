## Lernziele

Nach dieser Übung kannst du

- Linux-Server-Distributionen und Paketverwaltung funktional unterscheiden und einen Ubuntu-Server mit statischer Adresse, Route und DNS (netplan) in das Labornetz einbinden,
- Benutzer, Gruppen, Rechte und `sudo` einrichten sowie Systemdienste mit systemd anlegen, starten und bei Fehlern analysieren,
- den SSH-Zugang auf Schlüssel umstellen, eine Firewall (`ufw`) sicher aktivieren und Protokolle (`journalctl`) zur Diagnose nutzen.

## Voraussetzungen

- Modul 2 und 3: Labor läuft (`SRV-FS01` routet, `SRV-DC01` ist DNS-Server der Domäne).
- Dieses Modul nutzt **Internetphase I-3**: `LX-UBU01` bekommt nur zur Installation und für `apt` Internet; danach zurück ins Labornetz.
- **Sicherer Zustand:** Prüfpunkt `LX-UBU01-M5-Start` direkt nach der Installation (VM ausgeschaltet).

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **LTS** | Long Term Support: Ubuntu-Version mit langem Supportzeitraum (Zeitraum auf der Herstellerseite prüfen). |
| **netplan** | Netzwerkkonfiguration unter Ubuntu (YAML-Dateien in `/etc/netplan`). |
| **Setgid-Bit (`2xxx`)** | Neue Dateien im Verzeichnis erben die **Gruppe** des Verzeichnisses. |
| **systemd** | Dienst- und Startverwaltung; Units beschreiben Dienste. |
| **SSH-Schlüssel** | Schlüsselpaar: privater Schlüssel bleibt am Client, öffentlicher liegt in `authorized_keys`. |
| **ufw** | „Uncomplicated Firewall“: einfache Schnittstelle für die Linux-Firewall. |
| **Journal** | Protokoll von systemd, abfragbar mit `journalctl`. |

### Teil 2: Server installieren und einbinden

*(Lerneinheiten 5.4, 5.6, Praxisaufgabe 2)*

**1. VM anlegen** (Host)

```powershell
New-VM -Name LX-UBU01 -Generation 2 -MemoryStartupBytes 2GB -NewVHDPath D:\VMs\LX-UBU01\LX-UBU01.vhdx -NewVHDSizeBytes 30GB -SwitchName sw-lab-srv

```

**2. Internetphase I-3**

`NIC-LAB` trennen, `NIC-INET` mit dem `Default Switch` verbinden, Ubuntu Server 24.04 LTS installieren (Benutzer `labadmin`, Kennwort wird beim Installieren eingegeben). Danach:

```bash
sudo apt update && sudo apt upgrade
dpkg -l | grep -E "ufw|unattended-upgrades|openssh-server"      # Vorinstallation nicht bestätigt
```

Phase beenden: `NIC-INET` trennen, `NIC-LAB` verbinden.

**3. Adressen per netplan**

```bash
ls /etc/netplan/

sudo nano /etc/netplan/<Datei>.yaml
sudo chmod 600 /etc/netplan/<Datei>.yaml
sudo netplan try          # nicht bestätigt: automatische Rücknahme nach Zeitablauf
```

**Rückbau:** `sudo cp ~/netplan-backup.yaml /etc/netplan/<Datei>.yaml && sudo netplan apply`. Syntaxfehler zeigt `netplan generate` (im Testlauf mit Einrückungsfehler: „Invalid YAML: inconsistent indentation“).

**4. Testen**

```bash

getent hosts srv-dc01.lab.example.internal
```

Von `CL-W11-01`: `ping 192.168.50.30`. (Die Ping-Regel aus Modul 2 gilt nur für Windows; Linux antwortet standardmäßig, *nicht bestätigt*.)

### Teil 5: Eigener systemd-Dienst

*(Lerneinheit 5.5, Praxisaufgabe 5)*

```bash
sudo install -m 755 05.1-lab-hello.sh /usr/local/bin/lab-hello.sh
sudo cp 05.1-lab-hello.service /etc/systemd/system/lab-hello.service
sudo systemctl daemon-reload
sudo systemctl start lab-hello
systemctl status lab-hello
journalctl -u lab-hello -e
```

**Fehler analysieren:** Ändere `ExecStart` absichtlich auf `/usr/local/bin/lab-hallo.sh`, lade neu und starte:

```bash
sudo systemctl daemon-reload
sudo systemctl start lab-hello
systemctl status lab-hello
journalctl -u lab-hello -e
systemd-analyze verify /etc/systemd/system/lab-hello.service
```

Der Testlauf von `systemd-analyze verify` meldet: „Command /usr/local/bin/lab-hallo.sh is not executable: No such file or directory“. Korrigiere den Pfad.

**Rückbau:**

```bash
sudo systemctl disable --now lab-hello
sudo rm /etc/systemd/system/lab-hello.service /usr/local/bin/lab-hello.sh     # nur diese beiden Dateien
sudo systemctl daemon-reload
```

### Teil 6: SSH mit Schlüssel

*(Lerneinheit 5.6, Praxisaufgabe 6)*

1. Auf `CL-W11-01`: `ssh -V`. Fehlt der OpenSSH-Client (Standardlieferung *nicht bestätigt*), in Phase I-3 über „Optionale Features“ nachinstallieren.
2. Schlüsselpaar erzeugen (Passphrase interaktiv) und öffentlichen Schlüssel übertragen:

```powershell
ssh-keygen -t ed25519
scp $env:USERPROFILE\.ssh\id_ed25519.pub labadmin@192.168.50.30:/home/labadmin/
```

3. Auf `LX-UBU01`:

```bash
mkdir -p ~/.ssh && chmod 700 ~/.ssh
cat ~/id_ed25519.pub >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys
```

4. **Vor dem Abschalten der Kennwortanmeldung:** Teste die Schlüsselanmeldung in einer **zweiten Sitzung** und lass die erste offen. Erst dann:

```bash
sudo cp 05.1-ssh-lab-haertung.conf /etc/ssh/sshd_config.d/10-lab-haertung.conf
sudo sshd -t
sudo sshd -T | grep -iE "passwordauthentication|permitrootlogin"
sudo systemctl reload ssh          # Dienstname nicht bestätigt (evtl. sshd)
```

Teste eine neue Verbindung. **Warum `10-`?** Im Testlauf gewann bei `sshd -T` der **erste** Wert (Drop-in `10-` schlug `50-cloud-init.conf`). Bleibt `passwordauthentication yes` stehen, setzt eine andere Datei den Wert früher: Dateien in `sshd_config.d/` prüfen. **Notausstieg:** über die Hyper-V-Konsole (nicht über SSH) die Datei entfernen und `sudo systemctl reload ssh`.

*(Lerneinheit 5.7, Praxisaufgabe 7)*


### Teil 8: Härten

*(Lerneinheit 5.8, Praxisaufgabe 8)*

1. `sudo ss -tulpn` und dokumentiere **jeden Eintrag** (Dienst, Zweck, nötig ja/nein). Das Skript `05.1-haertung-pruefen.sh` liefert eine Übersicht.
2. Aktiviere `ufw` **nur mit zweiter offener SSH-Sitzung** und erreichbarer Hyper-V-Konsole:

```bash
sudo ./05.1-ufw-regeln.sh -n      # Trockenlauf
sudo ./05.1-ufw-regeln.sh         # fragt nach der zweiten Sitzung
```

Beide Quellnetze sind nötig: `SRV-FS01` routet ohne NAT, daher bleibt die Quelladresse von `CL-W11-01` `192.168.60.x`.
3. Teste die Verbindung von `CL-W11-01`. Prüfe `sudo sshd -T | grep -iE "permitrootlogin|passwordauthentication"`.
4. **Rückbau:** `sudo ufw disable` (über die Hyper-V-Konsole, falls der Zugang verloren geht). Am Ende Prüfpunkt `LX-UBU01-M5-Ende` bei ausgeschalteter VM.

## Hintergrund

### Distributionen im Überblick

Ubuntu und Debian nutzen Pakete im `.deb`-Format (Werkzeug `apt`/`dpkg`); Red-Hat-basierte Distributionen nutzen `.rpm` (Werkzeug `dnf`/`rpm`). Unterschiede bestehen im Veröffentlichungsrhythmus und Supportmodell; konkrete Zeiträume stehen auf den Herstellerseiten und ändern sich, deshalb gehören sie in deine Tabelle mit Quelle und Datum.

### Warum Setgid auf gemeinsamen Verzeichnissen?

Ohne Setgid erhalten neue Dateien die **primäre Gruppe des Erzeugers**. Mitglieder von `labgrp` könnten fremde Dateien dann nicht ändern. Mit Setgid (`2770`) erben Dateien die Gruppe `labgrp`; die Rechte `770` geben Besitzer und Gruppe Vollzugriff, allen anderen keinen. Im Testlauf entstand `-rw-rw-r-- 1 labuser01 labgrp`, ein Benutzer ohne Gruppenmitgliedschaft wurde abgewiesen.

### Warum daemon-reload?

systemd liest Unit-Dateien nicht bei jedem Start neu ein. Nach einer Änderung weiß es nichts davon, bis `systemctl daemon-reload` die Dateien neu einliest. Sonst startet es die **alte** Beschreibung.

### SSH: erst testen, dann abschalten

Wer die Kennwortanmeldung abschaltet, bevor die Schlüsselanmeldung funktioniert, sperrt sich aus (bei einer VM im Labor hilft die Hyper-V-Konsole, in der Praxis oft nur der Standort). Deshalb: zweite Sitzung offen lassen, Konfiguration mit `sshd -t` prüfen, wirksamen Wert mit `sshd -T` lesen.

## Hinweise

- Alle Änderungen haben einen Rückbau; die Skripte können mit `-n` (Trockenlauf) angesehen werden.
- Kennwörter nie in Dateien; `labuser01/02` werden ohne Kennwort angelegt und danach interaktiv mit `passwd` versehen.
- Ob die Ubuntu-Installation ohne Internet vollständig durchläuft, ist *nicht bestätigt*; deshalb liegt sie in Phase I-3.
- `netplan try` ist die sichere Variante; `netplan apply` übernimmt sofort.

## Prüfbefehle und Kontrollfragen

```bash
ip -br addr show lab0                              # 192.168.50.30/24
ip route | grep 192.168.60.0                       # via 192.168.50.20
getent hosts srv-dc01.lab.example.internal
ls -ld /srv/lab/shared                             # drwxrws--- ... labgrp

sudo sshd -T | grep -iE "passwordauthentication|permitrootlogin"
sudo ufw status verbose
```

**Kontrollfragen**

1. Wodurch unterscheiden sich Ubuntu LTS und eine Red-Hat-basierte Distribution in Paketverwaltung und Supportmodell?
2. Was bewirkt das Setgid-Bit (`2770`) auf einem gemeinsamen Verzeichnis?
3. Warum muss nach Änderung einer systemd-Unit `daemon-reload` ausgeführt werden?
4. Warum wird die Kennwortanmeldung per SSH erst nach einem erfolgreichen Schlüsseltest deaktiviert?
5. Warum braucht die ufw-Regel für SSH beide Quellnetze `192.168.50.0/24` und `192.168.60.0/24`?

### Antworten auf die Kontrollfragen

1. Ubuntu LTS nutzt `.deb`/`apt`, Red-Hat-basierte Systeme `.rpm`/`dnf`; Support und Rhythmus sind herstellerspezifisch (aus deiner Tabelle mit Quelle).
2. Dateien im Verzeichnis erben die Gruppe des Verzeichnisses (`labgrp`), nicht die des Erzeugers.
3. systemd liest Units nicht laufend neu; `daemon-reload` liest die geänderten Dateien ein.
4. Sonst droht die Aussperrung: Gelingt die Schlüsselanmeldung nicht, gibt es nach dem Abschalten keinen Zugang per SSH mehr.
5. `SRV-FS01` routet ohne NAT: Die Quelladresse von `CL-W11-01` bleibt `192.168.60.x`; Verbindungen aus dem Servernetz kommen aus `192.168.50.x`.

### Teil 5 (Fehlerbild)

`systemctl status` zeigt „failed“ mit `status=203/EXEC`; `journalctl -u lab-hello -e` nennt den nicht ausführbaren Pfad. Der Code 203/EXEC steht bei systemd für Startfehler des Befehls (*nicht bestätigt in dieser Umgebung*).
